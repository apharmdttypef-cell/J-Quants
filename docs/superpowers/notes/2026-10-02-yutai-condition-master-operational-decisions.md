# 優待条件マスタ: 運用上の決定と保留事項

記録日: 2026-10-02
対象ブランチ: `worktree-yutai-condition-master`(設計 `2026-10-01-yutai-condition-master-design.md`、計画 `2026-10-01-yutai-condition-master.md`)

実装11タスクは完了・レビュー済み。計画の Task 12(デプロイと本番データ投入)は**未実行**。
ここには、実装中に決めたが**コードを読んでも分からない**判断を残す。

## 1. 再取得キューを誰も消費しない(保留)

`yutai-tdnet-watch-batch` は優待変更を検知すると `conditionCheckedAt` を REMOVE し、
その銘柄を「個別ページ再取得待ち」にする。しかし `yutai-detail-sync-batch` は設計通り
EventBridge スケジュールを持たないため、**このキューを自動で消費するものは無い**。
さらに `conditionCheckedAt` は API に出していないので、「変更検知済みだが未再取得」の
状態は画面からも見えない。

**判断: 今回は保留**(2026-10-02、利用者の判断)。理由は、最初の全件取得が終わるまで
そもそもキューが積まれないため。実運用を見てから次のいずれかを決める。

- `yutai-detail-sync-batch` に月次スケジュールを付ける(1,642銘柄で約33分。サイトへの
  負荷は月1回・1リクエスト/秒なので許容範囲)
- `conditionCheckedAt` を API に出し、陳腐化を可視化するだけにする(自動化しない妥協案)

## 2. ロールバック時に `unitShares` が再汚染される

Task 12 の移行後にこのブランチを revert すると、`estimateRequiredShares`
(`minInvestment ÷ 株価` を丸める推定)が復活し、**次の日次バッチ実行で `unitShares` が
再び 200/300 に汚染される**。

復旧は `yutai-master-sync-batch` を手動実行すれば済む(`unitShares: 100` を無条件に
書き戻す)が、気付かないと一覧の必要資金と前回逆日歩が静かにずれる。revert する場合は
**その直後に `yutai-master-sync-batch` を実行する**こと。

## 3. バッジ不一致の行は「不明」表示だが、絞り込みは「可」のまま

一覧ページのバッジと個別ページの解析が食い違った銘柄(`benefitParseWarning` に
`badge-mismatch` を含む)は、**表示だけ**「不明」に倒している。誤った「可」は
「買ってクロスして逆日歩を払って優待ゼロ」という取り返しのつかない損失になるのに対し、
誤った「長期のみ」は機会損失で済む — コストが非対称だから安全側に倒した
(2026-10-02、利用者の判断)。

保存値 `crossEligible` の優先ルール(個別ページの解析結果を採用)は**変えていない**。
その結果として、**「不明」と表示されている行は、サーバ側の「可」絞り込みにはヒットし、
ソートでも「可」のグループに並ぶ**。表示と絞り込みが一致しないので、不一致銘柄が増える
ようなら絞り込み側も合わせるか検討する。

## 4. バケットがタイムアウトしても再試行されない

`yutai-detail-sync-batch` を Step Functions の Map で9バケットに分けているが、
Lambda のタイムアウトは `Lambda.Unknown` として現れ、**どのリトライ条件にも一致しない**。
バケットが1つタイムアウトすると実行全体が失敗し、**後続のバケットは走らない**。

`conditionCheckedAt` により再実行は冪等なので、対処は「実行をもう一度起動する」だけでよい。
成功済みの銘柄は取り直されない。この点は Task 12 の手順にも書いてある。

なお、明示的な `addRetry` は削除した。`LambdaInvoke` のコンストラクタが
`Lambda.ServiceException` 等に対して先にリトライを登録し、Step Functions は最初に一致した
ものを使うため、明示指定は死んでいた(aws-cdk-lib 2.263.0 のソースで確認)。

## 5. 1リクエスト/秒は構造的に担保した

`reservedConcurrentExecutions: 1` を付けたので、オペレータが「失敗したと思って」実行を
二重起動しても、2本目は `Lambda.TooManyRequestsException` で弾かれる(これは明示リトライを
削除した後も既定のリトライが拾う唯一のエラーではない点に注意 — 弾かれた呼び出しは
Step Functions 側のリトライ対象になる)。

待機は固定1秒ではなく「前回リクエスト開始からの経過を差し引いた残り」にしてあるので、
ページ取得が遅い日でも1リクエスト/秒を保ったままバケットの所要時間が伸びない。
