# taisyaku.jp CSVの残高列 実機確認(Task 0)

`fetchTaisyakuCsv('9418', '2026-06-01', '2026-08-28')`を既存コードでそのまま実行し、実際のCSVを取得して確認した。

## ヘッダー行(実物、全27列)

```
"銘柄コード","銘柄名","直後基準日","直近制限措置","直近臨時措置","直近特別措置","申込日","市場区分","貸借区分","融資新規（株）","融資返済（株）","融資残高（株）","貸株新規（株）","貸株返済（株）","貸株残高（株）","差引残高（株）","貸借値段（円）","品貸料率（品貸日数分/円）","品貸日数","品貸料率（年率換算/％）","最高料率（品貸日数分/円）","最低料率（品貸日数分/円）","応札ランク","制限措置","臨時措置","特別措置","新株引受・権利入札"
```

設計書・実装計画は「融資残高」「貸株残高」等11列程度の簡略ヘッダーを想定していたが、実物は27列。ただし`parseTaisyakuCsv`の列探索は固定位置ではなく「`融資`と`残高`を両方含む列」のようなマーカー方式なので、列が増えていること自体は実装に影響しない。**Task 1のテストのCSV例は、この実物のヘッダー・行をそのまま使う形に置き換える**(以下に反映済み)。

**括弧は全角(`（　）`)**。設計書・実装計画の元のテスト例は半角`( )`で書かれていたため、実物に合わせて全角に直す必要がある(マーカー検索自体は括弧を見ていないので実装ロジックには影響しない)。

新たに存在する、設計書が想定していなかった列: `最低料率（品貸日数分/円）`(最高料率と対になる下限)、`特別措置`(制限措置・臨時措置とは別の3つ目の措置区分)、`直近制限措置`/`直近臨時措置`/`直近特別措置`(行の措置とは別の「直近」サマリ列、先頭寄り)、`新株引受・権利入札`。今回のスコープでは`最高料率`・`応札ランク`・`制限措置`・`臨時措置`のみ取り込む設計判断のままでよい(YAGNI。特別措置等は将来必要になったら追加)。

## 確認結果(設計書の想定との差分)

1. **桁区切りカンマは実データで一度も観測されなかった**。3ヶ月分・63行(融資残高/貸株残高が最大約200万まで)を確認したが、`"1,234,567"`のようなカンマ区切りは1件もない(すべて`"2039300"`のような素の数字文字列)。設計書は「桁区切りカンマ対策としてクォート考慮パーサが必要」としていたが、この根拠(カンマ区切りの実在)は今回の実機確認では**裏付けられなかった**。ダブルクォートで全フィールドが囲まれていること自体は確認済みなので、クォート除去(`stripQuotes`、既存実装のまま)は必要。クォート内カンマを区別する`splitCsvLine`は当面のデータでは出番がないが、実装しておくこと自体は無害(将来カンマ区切りの列が出てきても壊れない防御)なので、Task 1の実装は計画通り進めてよい。テストは「カンマ区切りの実例」ではなく「実物に忠実な非カンマの実例」を主に置き、カンパ区切り入力への耐性テストは"仮に将来カンマ区切りが来ても壊れない"という防御的テストとして別枠で残す。

2. **`差引残高` = `融資残高 − 貸株残高`(貸株残高が多いほどマイナス)と確定した**。8/27行で検算: 融資残高1,100 − 貸株残高2,039,300 = −2,038,200 = CSVの差引残高と完全一致。したがって`差引残高`の符号は設計書が定義する`excessRatio`(貸株超過が正)とは**逆符号**。設計書の方針(差引残高は保存のみ・計算には使わず`lendingBalance - financingBalance`を自前計算する)は正しかった。実装時にこの符号を反転させて使わないよう要注意。

3. **想定外の値`"*****"`を発見(重要)**。8/21行で`品貸料率(品貸日数分/円)`と`品貸料率(年率換算/％)`の両方が`"-"`ではなく`"*****"`になっている。この日は融資残高=貸株残高=26,100で**差引残高がちょうど0**(貸株超過も融資超過も無い、唯一の境界日)。応札ランクは他の「実績なし」日と同じく`"-"`。63行中この1行のみで観測(頻度は低いが実在する)。`最高料率`列自体は`"7.20"`と通常通りの数値が入っている(マスクされているのは実績の品貸料率・年率のみ)。

   **設計書・実装計画の`occurred`判定(`品貸料率が'-'以外`)はこのケースを見逃す**: `Number('*****')`は`NaN`になるが、判定条件が文字列`'-'`との比較のみだと`"*****"`は`occurred: true`側に倒れ、`totalAmount`等がNaNになる恐れがある。**Task 1の実装を、「'-'と等しいか」ではなく「数値として parse できるか(NaN判定)」に変更する**必要がある(以下、Task 1修正に反映済み)。これにより`'-'`・`'*****'`・将来出てくるかもしれない他のマスク文字列を一律に「occurred: false」として扱える。

## 未確認のまま残った点

- `"*****"`が具体的に何を意味するか(taisyaku.jp側の仕様としての正式な説明)は未確認。差引残高=0の境界日にのみ観測されており、「超過ゼロで入札自体が成立しない/計算できない」ことのマスク表示という仮説を置いているが、公式ドキュメントでは確認できていない。低頻度(1/63)なので実害は小さいと判断し、`occurred: false`として扱う保守的な方針で進める。
- 特別措置・新株引受権利入札列は今回のサンプル期間中すべて空欄で、実際の値の入り方は未確認。
